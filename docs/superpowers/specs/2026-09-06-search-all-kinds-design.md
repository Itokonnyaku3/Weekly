# 検索を全種類に広げる（設計）

- 日付: 2026-09-06
- 対象: `v2/src/search.js`, `v2/src/query.js`（＋検索バーのUI）
- 位置: 第2段（到達性）の項目1／全4項目のうち最初
- 状態: 設計提示中

## 背景

タスクの正データを Weekly v2 に一本化する方針（[2026-09-06-outline-scope-guard-design.md](2026-09-06-outline-scope-guard-design.md) の背景を参照）のうち、第1段「編集操作の信頼性」は完了。本仕様は第2段「到達性」の最初の項目。

### 実データで測った到達性（`v2/tracker.json`, 2026-07-31 時点・本体1286件）

| 種類 | 計 | 自分にタグ | 祖先のタグで拾える | PJページ配下 | 到達不能 |
|---|---:|---:|---:|---:|---:|
| memo | 960 | 220 | 184 | 165 | **391** |
| task | 208 | 162 | 8 | 3 | **35** |
| image | 47 | 0 | 8 | 0 | **39** |
| table | 9 | 0 | 5 | 4 | 0 |

到達不能は計 **465件**、**111個の塊**に分かれる。上位15塊で261件（56%）を占め、60塊は1件のみ。

**画像が最も深刻。** 47枚のうち39枚は、日ツリーを手繰る以外に到達する方法が無い。リストは `kind === 'task'` のみ（`list.js:297`）、検索は memo と task のみ（`search.js:11`）で、どちらにも出てこない。

### なぜタグが付いていないのか

ユーザーの言葉: **「メモした時点では、どの切り口でチェックしたいのか分からない」**

書く時点で軸が決まらないため、「書くときに正しいタグを付ける」設計は原理的に成立しない。実データもそれを裏づけている。同じ会議が毎回違う表記で書かれており（「1000 リーダー会」「デジタルリーダー会議」「デジ推リーダー会」等、8回すべて表記違い）、文字列一致では結合できない。表記揺れの吸収は AI 機能（[BACKLOG-ai.md](../../BACKLOG-ai.md) の①）に委ね、本仕様では扱わない。

### 第2段の全体像（この順序）

1. **検索を全種類に広げる** ← 本仕様。タグ付け作業ゼロで到達性が改善する唯一の項目
2. 無タグの塊の棚卸し画面（上位15塊で56%が片付く。UI形式は着手時に決める）
3. タグの一覧とタグから引く導線
4. 俯瞰ビュー（保存クエリを並べた画面）

第2の軸は**新設しない**。既存の `#タグ`（`props.js` の `cardTags`、`query.js` の `tags[]`、`#` の候補表示、`TAG_SCHEMAS`）を「場」の軸として使う。1286件中29件しか使われていないのは機能が無いからではなく、付ける導線が無いため。

## 現状の作り

`search.js` は既に必要な土台を持っている。**結果の表示側は変更しない。**

- `matchCard(body, query, today)` … `kind` が memo/task 以外なら `false`。それ以外は `matchQuery`（`query.js`）へ委譲
- `runQuery(store, query, today)` … 一致した body を集め、**祖先も一致するものは除外**して最上位だけ返す
- 描画 … `sourceDay()` で出所の日付ごとにグルーピングし、`renderChildren` で編集可能なミラーとして表示。`↗` で元の場所へジャンプ

つまり **「種類=画像」で引ければ、47枚が日付ごとに並び、その場で編集でき、元の場所へ飛べる**。土台は既にある。

## 設計

### 1. `matchCard` の種類ゲートを差し替える

```js
// 検索の対象外: day と project は「器」なので結果に出さない。
// 特に day を含めると、条件なし検索で全 day が最上位一致になり、
// runQuery の祖先除外によって配下すべてが消える（＝検索が壊れる）。
const SEARCHABLE = new Set(['memo', 'task', 'image', 'table']);
```

`day` と `project` を除外することが**必須**。理由は上のコメントのとおり。`project` はプロジェクトビューから到達できるため、検索結果に出す必要がない。

### 2. `query.js` に `kind` 条件を追加する

```js
// group = { keyword, tags[], proj, mid, due, done, prio, kind }
//   kind: 'all'（既定）| 'memo' | 'task' | 'image' | 'table'
```

`defaultGroup()` に `kind: 'all'` を追加。`matchQuery` に照合を追加する。既定が `'all'` なので、**既存の保存検索とリスト（表）の挙動は変わらない**（`list.js` は独自に `kind === 'task'` で絞っているため影響なし）。

### 3. キーワードは画像・表に適用しない

画像の `body.content` は `v2-data/img/img_1782356143821.png` のようなリポジトリ内パス。これをキーワード照合の対象にすると「img」「2026」等で全画像が誤ヒットする。

```js
// 画像/表は本文を持たない（content はパスや表データ）。キーワード条件が
// 指定されているときは一致させない。パス文字列へのヒットは意味がなく
// ノイズになるため。種類・タグ・PJ・期限の条件では通常どおり対象になる。
```

したがって「種類=画像 かつ キーワード=バーコード」は0件になる。論理的には正しい（画像は文言を持たない）。

**将来の改良案（本仕様では実装しない）:** 画像・表を「親カードの文言」で引けるようにする。`runQuery` は store を持つので祖先の文言を取れるが、`matchCard` の引数が増えてテストにも波及する。まず種類フィルタだけで運用し、必要が確認できてから足す。

### 4. 検索バーに「種類」のドロップダウンを足す

既存の「期限」「完了」「優先度」と同じ `selectEl` + `labelWrap` の並びに追加する。選択肢は `すべて / メモ / タスク / 画像 / 表`。

ヒント文（`search-hint`）の「全カード（メモ/タスク）から絞り込み」を、全種類が対象になった旨に更新する。

## 得られる状態

- **タグを1つも付けずに**、画像47枚・表9件へ到達できる（種類で絞れば日付ごとに一覧できる）
- 項目2（棚卸し）の作業中に、検索で現物を確認しながら進められる
- 項目3・4（タグ導線・俯瞰ビュー）が全種類を対象にできる土台になる

## テスト

`v2/tests/search.match.test.mjs` と `v2/tests/query.test.mjs` に追記する（新規ファイルは作らない。既存の対応するテストに足す）。

- `matchCard`: memo/task/image/table は対象、`day` と `project` は対象外
- `kind: 'all'` は全種類に一致（既定値の後方互換）
- `kind: 'image'` は画像だけに一致
- キーワード指定時、画像・表は一致しない（パスへの誤ヒットが無いこと）
- `kind` 未指定の既存クエリが従来どおり動く（デグレ検出）
- `runQuery`: `day` を除外しているため、条件なしでも配下のカードが消えないこと

検証: `cd v2 && node --test "tests/*.test.mjs"`。現在のベースラインは 45 pass / 0 fail。

## スコープ外

- リスト（表）の対象拡大。タスクの表に画像を並べても意味がないため、リストは `kind === 'task'` のままにする。全種類の受け皿は検索ビューとする
- 画像・表を親の文言で引く改良（上記3の将来案）
- 会議の表記揺れの自動吸収（AI機能①）
